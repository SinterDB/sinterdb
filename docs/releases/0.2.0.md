## Storage Reliability

SinterDB 0.2.0 hardens what happens to your data when things go wrong. You can
choose how much a write must survive, take checked backups, look inside a data
directory that will not open, repair it, and trust that a full disk or a killed
process leaves the database in a state it really had. The driver API and the
wire protocol are the same as in 0.1.0, and a 0.1.0 data directory opens as it
is.

```bash
npm install --global @sinterdb/cli
npm install sinterdb
```

Start with the [quick start](../quick-start.md).

### Highlights

- **Write concerns.** `--write-concern` takes `flushed` (the default: on stable
  storage before the reply), `journaled` (handed to the operating system) or
  `memory` (applied in memory and logged within about 100 ms). They replace the
  `fsync` and `buffered` durability modes, which still work. See
  [Durable storage](../storage.md#write-concerns).
- **Group commit.** With `flushed`, writes that arrive together share one flush,
  and every reply is held until it is done, so many clients write faster with
  the same guarantee.
- **Backup and restore.** `sinterd backup`, `sinterd verify-backup` and
  `sinterd restore` copy a data directory into a backup that is checked file by
  file with SHA-256 checksums. A restore proves the copy recovers before it
  puts it in place. See [Backup and restore](../backup.md).
- **Inspect and repair.** `sinterd inspect` reports the state of a data
  directory without changing it: the manifest, the lock, every snapshot and
  log segment, and whether the server could open it. `sinterd repair` shows a
  plan first. It moves what it removes to a `quarantine` folder instead of
  deleting it, and only discards log records when you pass `--allow-data-loss`.
  See [Inspecting and repairing](../repair.md).
- **Safer checkpoints.** The manifest is replaced atomically. Automatic
  checkpoints run in the background, so a large data set does not stop reads
  and writes while it is saved. `--checkpoint-interval` adds a clock to the
  size rule, and `--checkpoint-keep` sets how many snapshots stay on disk.
- **Disk-full and permission errors.** A full disk is reported as a clear
  error, leaves no half-written file behind, and does not stop the server from
  serving reads or from accepting writes once space returns. A write that
  cannot be flushed is never guessed at: the server stops and recovers the true
  state from disk on the next start.
- **Upgrades that survive a crash.** A storage format migration framework marks
  the manifest while it rewrites files, so an upgrade interrupted halfway is
  finished by the next start. No migration is needed for this release.
- **Failure testing.** Tests kill the process during writes and checkpoints,
  fail every file system call of a workload in turn with a disk error or a full
  disk, cut the log at every byte and damage data files one byte at a time.
  After each, the directory must reopen with a state it really had. See
  [Failure testing](../storage.md#failure-testing).
- **Readable terminal output.** On a terminal, the server logs and the backup,
  inspect and repair commands print aligned, colored output. Piped or redirected
  output is unchanged, and `NO_COLOR` and `FORCE_COLOR` are honored.

### Fixes

- A lock file is no longer left behind when writing it fails.
- A failed backup copy no longer leaks a file handle.

### Upgrading from 0.1.0

No data or protocol format changed: storage format 2, snapshot format 2, WAL
format 1, and protocol 1 are the same. Still copy the directory, or better, make
a checked backup with `sinterd backup`, before you try a new version.

What to know, each with what to do:

- `--durability` and `SINTERDB_DURABILITY` are deprecated. Use `--write-concern`
  and `SINTERDB_WRITE_CONCERN`. Setting both an old and a new option is an
  error, and the `server.started` log line reports `writeConcern` instead of
  `durability`.
- On a terminal the log is no longer JSON. Anything that reads the log from a
  file or a pipe still gets one JSON object per line.

The [migration notes](../compatibility.md#migration-notes) list all of them.

### Not yet

SinterDB is a developer preview for local projects. It has no authentication or
TLS, so keep it on `127.0.0.1` or a network you trust. It keeps the whole
dataset in memory, and backups still need the server stopped. See
[Known limitations](../limitations.md) before you depend on it.
